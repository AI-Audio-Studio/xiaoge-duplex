## 5. 打断恢复（flush 路径）

baseline 回退检测到 **15 次 flush**（打断 `ctrl.clear` → pause/flush/play，帧计数器归零重计）。这些轮 w2p = 60~218ms（中位 **136ms**）——**打断后下一轮起播不付额外成本**，`forceNewUtteranceMarker` 路径工作正常。

## 6. 离群点归因（全部可解释）

**>200ms 的 4 轮**：

| 轮次 | w2p | 原因 |
|---|---|---|
| #3 | 233ms | 无布防的 agent 连续段，管线闲置 ~3s 后半温起播 |
| #5 | 200ms | 说完估计漏检（该轮无 mic_end），stt 兜底跑道仅 387ms，勉强赶上 |
| #59 | 218ms | flush 后帧计数器刚归零（baseline=0），下游首 scoop 稍慢 |
| #61 | 206ms | 同 #59，打断紧后沿的边界情形 |

**<10ms 的 4 轮（w2p=1~2ms）**：首写瞬间恰有预热静音在途，首写后首次采样即越过基线——测得的是在途静音的呈现时刻（文档已注明的 ≤40ms 测量偏差）。这 4 轮实际是**管线最热**的最佳情形。

## 7. 结论与建议

1. **客户端优化目标达成且稳定**：w2p 中位 134.5ms、p90 155ms，两份日志（8 轮 / 62 轮）互相印证，与 vnine 真机结论（中位 143ms）一致。此 ~135ms 为 deep-buffer 混音器节拍的地板，App 层无解。
2. **剩余时延 92% 在服务端**：断句等待（~1.6s）+ 首包生成（~630ms）。继续压缩需服务端缩短 VAD 尾部静音或提前 TTS 起播。
3. **Watch item**：说完估计 RMS 大量贴线（min 250、中位 291，见附录），本轮出现 1 次漏检（#5）。若后续慢轮增多且该轮无 `mic_speech_end`，将 `SpeechEndEstimator.SPEECH_END_ABS_RMS` 从 250 降至 **~200**。
4. **agent 连续段（#3/#15 类）**是目前唯一无布防场景，w2p 上限 233ms 可接受；若产品上这类分段回复变多，可考虑开启 `AudioEngine.KEEPALIVE_ENABLED` 心跳覆盖（默认关闭的决策在此样本下依然合理，2/62 的发生率不值得常开）。

## 附录 B：埋点口径

logcat tag `XiaogeAudio`，`latency_node=` 前缀：

| 节点 | 含义 |
|---|---|
| `mic_speech_end` | 本地说完估计触发（RMS>250、≥250ms 语音+300ms 静音），领先服务端断句 1~3s |
| `stream_prewarm_armed` | 预热布防（来源：mic 估计 / stt_final / engine 启动） |
| `tts_first_write` | 回复首包写入 AudioTrack（utterance 首写） |
| `playback_first_presented` | 首帧进入输出通路；`firstWriteToFirstPresentedMs` 即 w2p |

测量注意：w2p 含 ≤40ms 在途静音垫底偏差（持续预热下首写可能落在静音流中段）；`presented` 是框架级"交给输出通路"时刻，非扬声器出声时刻。
