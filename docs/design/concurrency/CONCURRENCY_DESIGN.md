## 3. 背景、目标与部署形态

**背景**:当前服务器部署(`WEB_AUDIO=1`+TLS)一次只服务一个用户,第二个连接被 busy 拒绝。

**目标**:同一台服务器并发 N 路独立语音会话(每路=完整 STT/LLM/TTS/打断/录音链),
**浏览器多用户为第一场景**,协议客户端共池;会话互不串音、互不拖延迟。

**非目标**:多机集群、鉴权计费(最低准入除外,D-18)、会话持久化、断线续会话(D-07;
浏览器刷新宽限窗 D-16 是网关侧特性,非协议变更)。

**部署形态(建模基础)**:
- PC/服务器形态开关 = `WEB_AUDIO`(0=本地声卡;1=浏览器音频),服务器形态叠加
  `WEB_UI_HOST`(公网)+ `WEB_SSL_CERT/KEY`(TLS)。同一代码库、纯 env 分形态。
- 一个 aiohttp app 同时服务两类接入:**浏览器用户**(`GET /` + `/ws` + `/ws/audio` +
  `POST /api/*`,一个用户=一组必须落同一进程的请求)与**协议客户端**(C/MATLAB/Python,
  仅 `/ws/audio`,一连接一会话)。
- 线上代码=重构前;本设计基线=重构后 main@735db1a → WP-0(D-02)。

## 5. 目标架构(A1)

```
[浏览器 https/wss]──┐
[C/MATLAB/Python]───┤
                    ▼
        ┌──────────────────────┐     ┌─────────────────────────┐
        │  网关(§6)            │     │  池管理器(§7)           │
        │  TLS 终结·准入·亲和  │◄───►│  预热/healthz/回收/告警  │
        │  路由/宽限窗/限流    │     │  转码旁路任务(D-13)     │
        └──────┬───────────────┘     └───────────┬─────────────┘
               │ 127.0.0.1:191xx(仅内网)          │ spawn/env 注入/退出指令
               ▼                                  ▼
        [P1] [P2] … [Pn]  ← 每进程 = 今天的单会话 agent,全路由(D-03)
                             写 WAV+timeline 到 recordings/<id>/
```

职责边界:**网关**管连接(谁进来、去哪个进程、何时算断)、**池管理器**管进程(生死、
健康、回收、转码)、**agent 进程**管会话(与今天单会话行为 100% 一致,六处外围小改,
主链零改动;第 6 处为一行默认值)。

**方案对比结论**(完整对比见存档 v3 §6):A1 隔离性最好、客户端零改动、行为等价直接
继承 49 次回放验证、最快交付;成本是内存(每进程重复载判停模型)。A2/B 见 §15 演进路线。

## 6. 网关规格

### 6.1 路由规则(六条,单一对外端口,TLS 终结)

1. **`GET /` 无亲和 cookie**(新浏览器用户):先过**最低准入**(D-18:静态口令/邀请码,
   一次输入,随 cookie 免重复)→ 分配空闲进程、种亲和 cookie(`xg_aff=<proc_id>.<hmac>`)
   → 返回页面。**静态页由网关直接托管**,后端只透传 `/ws`、`/ws/audio`、`/api/*`。
   池满 → 静态**繁忙页**+自动重试脚本(不能等页面加载后才在 WS 里收 busy)。
2. **`/ws`、`/ws/audio`、`/api/*` 带亲和 cookie**:反代到 cookie 绑定进程。cookie 无效/
   进程已亡 → **拒绝并强制回页**:WS 关闭码 4001 affinity-lost、`/api/*` 返 409/410,
   前端脚本收到即整页刷新,由规则 1 统一重新分配。**重分配只发生在规则 1 单入口,
   状态/音频两通道永不分家**(WS 101 响应的 Set-Cookie 不可依赖,不做握手种 cookie)。
3. **`GET /ws/audio` 无 cookie = 协议客户端**:直接分配空闲进程;池满回 WS `busy` 消息
   (PROTOCOL 语义,三端 SDK 无感)。两类客户端天然共池;协议端预留容量=网关配额参数。
4. **`GET /ws` 无 cookie**:明确拒绝(同规则 2 关闭码)——状态通道无独立合法使用场景。
5. **待定断开 = 浏览器刷新宽限窗(D-16)**:带 cookie 的 `/ws/audio` 断开后,网关置该
   会话为"待定断开"保持 **T 秒(10~15s,实施定)**:窗内同 cookie 重连 → 接回**原进程**,
   会话与历史延续(宽限期会话静默等待,不回放缺失段);超时 → 才向 agent 下发退出。
   状态由**网关持有,agent 完全无感**;协议客户端不受影响(即断即杀,D-07)。
   **实现关键(T2)**:宽限窗内网关对该进程的**内部上游 WS 保持连接不断开**,重连后把
   新客户端 WS **接回既有上游连接**(帧续接)——若上游同断再重开,agent 的"断开即退出"
   立即触发,宽限窗形同虚设。
6. **双标签页防串**:同 cookie 已有活跃音频连接时,再次发起页面/音频连接 → 返回"已在
   另一窗口通话"提示页(WS 则拒绝),不透传 agent。

### 6.2 安全(R6 + D-18)

①`/api/*` 按**白名单**转发(mic/asr/tts),未知路径默认拒绝;②亲和 cookie
`Secure + HttpOnly + SameSite=Strict`;③每连接**消息速率与帧大小上限**;④拒绝/错误
响应**不泄漏内部拓扑**(端口/进程号/路径),含错误口令的响应。

### 6.3 故障模型(R4,网关侧)

网关独立进程,systemd 自拉;**网关崩溃 = 现存会话全断、不保留**(重启后浏览器全员回页、
协议客户端重连;明确不做会话迁移);亲和 HMAC key 随重启失效 → 全员按新用户回页
(可选 key 落盘持久化,实施定)。

### 6.4 实现选型

asyncio 自研(aiohttp 反代 + WS 双向透传 + cookie 亲和表,与 `clients/python` 同栈);
nginx 方案(cookie map + auth_request + 动态 upstream)复杂度不低于自研且分配策略弱,
不采用。对内明文(内部端口仅 127.0.0.1,§7.2)。

## 7. 池管理器规格

### 7.1 池策略

- 预热池 **size = 目标 N + 1~2 备用**(吸收回收风暴窗口);冷启动 ~10s 池内摊平。
- 就绪/健康探测走 **`GET /healthz`**(D-04):不占 WS 槽、无会话副作用;禁止用
  `/ws/audio` 握手当探测(反例:每次探测杀一个进程)。
- **会话结束 → 重启进程回收**(比状态复位可靠):"断开即退出"仅对带网关会话标记
  (`X-XG-Session: <id>`)的连接生效;浏览器会话由网关在**宽限窗超时后**才下发退出
  (D-16)。崩溃自动补位;"就绪进程数 < 阈值"告警。
- **活性判定**:以 WS 心跳(PROTOCOL 30s ping/pong)为准,**不得按"无业务流量"杀会话**
  (聆听模式下行可长时间静默);断开先进宽限窗。
- **故障模型(R4)**:池管理器独立进程,systemd 自拉,与网关互不连坐。

### 7.3 转码旁路任务(D-13,在池管理器侧,不在 agent 内)

扫描 `recordings/<id>/` 的 WAV → 转码(Opus;`flac` 能力保留)→ **校验**(D-21:FLAC
采样数逐一相等 / Opus 时长差 ≤1 编码帧)→ 通过才删源,失败**保底留 WAV**(绝不丢审计
数据)。**并发 ≤1~2、低优先级**(D-22),排队深度/积压时长入监控(§11)。与 agent 进程
生死完全解耦:会话结束进程立即退出不受转码拖累;转码器崩溃不影响在线会话。
编码实现用 **PyAV**(livekit-agents 既有依赖,零新增)。

## 8. agent 侧改动规格(六处外围小改,主链零改动)

> 实施须先过双重门。验收总口径:PC/测试形态行为不变;三开关默认值=现状
> (`WEB_UI_PORT` 默认值按 D-23 例外:8765→8787)。**"不变"的可测口径(A2-4 勘误)**:
> **非重采样轨 + manifest 逐字节一致**;**重采样轨允许 ≤2 LSB 差**——这是 `rtc.AudioResampler`
> (LiveKit 原生 HIGH 重采样)既有的非 bitwise 可复现性(旧代码自比亦 ±2 LSB),与本改造无关,
> 裸 bytewise 比对会误报,集成评审按此口径。

1. `runs/`/`recordings/` 目录名加进程/会话短 id(防同秒撞名);
2. 新增 `GET /healthz` 轻路由(返回 agent loop/会话就绪状态);
3. 带网关会话标记的 `/ws/audio` 断开 → 结束会话并退出进程(配合重启回收;非标记连接
   不触发);
4. 指标日志行加 session_id;
5. **录音与审计产物子系统**:
   - (a) **档位**:三轨录音器(TestRecorder)从 timeline 模式**解耦**为可独立启用 +
     `full/single/off` 分支。**不得**用 `AGENT_TIMELINE=1` 换取三文件——那会把
     timeline.jsonl/turn_kpis.json 等测试产物带进生产(违反"测试功能 opt-in、不碰
     正常流"硬约束);

## 11. 运维:监控、降级与合规

**监控七项与告警**(R7;阈值为建议初值,实施定):

| 指标 | 告警建议 |
| --- | --- |
| 就绪进程数 | < 池 size 的 50%(或 <2) |
| 池分配/回收速率 | 回收持续大于分配(池在漏) |
| `recordings/` 磁盘水位 | >70% 预警;>85% 触发降级 `single` |
| 转码积压深度/最老任务时长 | 积压 > 池 size,或最老任务 >30min |
| FunASR 连接失败率 | 5min 窗 >5% |
| DashScope 错误/限流率 | 5min 窗 >5% |
| 网关活跃会话数 | 达 N(容量满)持续 10min |

另:网关输出 session_id→进程映射表;各进程指标日志行内带 session_id,汇总脚本离线对账。

**容量/磁盘降级阶梯**(全部运维开关动作,无须改代码/重启全池):
`full`+`opus` → `single`+`opus` → `off`(`flac` 为可选无损档;转码失败保底 WAV 造成的
占用回升计入水位告警)。

**压力最大单一场景**:N 路同时断开(网关重启/批量断开)= 池回收风暴 + 转码排队 + 新连接
busy **三者叠加**——池备用容量、转码限流、繁忙页应答共同兜底,§12 回归以"批量断开"
专项一次覆盖三者。

**录音合规(开放子项)**:保留期限与访问控制待产品/合规结论;结论前按 D-20 临时策略
执行(仅落盘不外发、目录权限最小化)。

## 15. 演进路线(A2 / B)

- **A2(LiveKit 原生 worker,中期)**:每用户一 room,框架 proc_pool 派 job,判停模型
  全 worker 共享(内存 ~0.4GB/会话);客户端经"WS↔room 桥"平滑过渡(D-17),A1 网关
  届时演化为桥,投资不作废。**触发信号**:N 持续增长使内存成本显著、产品提出"重连续
  会话"(协议级变更)、需要多机/正规调度。
- **B(进程内多会话)**:内存增量最小(~0.1GB/会话)但改动面最大、故障连坐、GIL 实时性
  需专门压测——仅在 A2 落地后作为 job 内小并发(1 进程 2~4 路)优化项再议。
