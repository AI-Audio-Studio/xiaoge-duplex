# 小歌服务器并发改造 · 分析与设计（v1，待评审）

> 2026-07-04。**纯分析与设计,未改任何工程代码。** 以 main@735db1a(2026-07 重构合入后)为基线;
> 资源数字全部来自实测(RESOURCE_REPORT.md、REGRESSION_LOG.md §5)。

## 1. 背景、目标与非目标

**背景**:当前服务器部署(60.205.197.165:10099,`WEB_AUDIO=1`+TLS,C/MATLAB/Python 客户端按
`clients/PROTOCOL.md` 接入)**一次只服务一个用户**——第二个连接被 busy 拒绝。要支撑多用户,
需做并发改造。

**目标**:同一台服务器并发服务 N 路独立语音会话(每路 = 完整的 STT/LLM/TTS/打断/录音链),
会话间互不串音、互不拖延迟;N 由硬件与远端依赖容量决定,设计需给出容量公式。

**非目标(本轮不做)**:横向多机扩展/负载均衡集群、用户鉴权与计费、会话持久化。

## 4. 资源模型与容量测算（实测基础)

单会话实测(2026-07,Ultra7/16GB,进程树口径):

| 组件 | CPU(单核%) | RAM |
| --- | --- | --- |
| 监督进程 | ~0 | 4MB |
| 工作进程(会话本体) | IDLE:KWS开(threads=1) ~99%;KWS关 ~13%;ACTIVE 增量 ~+20% | ~360MB |
| 推理执行进程(turn-detector 常驻) | ~0(按轮触发) | ~800MB |

**容量公式**(K=是否开 KWS,单会话 CPU ≈ K×1.0+0.35 核,预留 30% 余量):

| 方案 | RAM/会话 | CPU/会话 | 8核16GB 示例 | 32核64GB 示例 |
| --- | --- | --- | --- | --- |
| A1(每会话一进程) | ~1.2GB | KWS开 ~1.35核 / 关 ~0.35核 | KWS开:min(13,4)=**4 路**;关:min(13,16)=**13 路** | KWS开 ~16 路;关 ~50 路(RAM 限) |
| A2(LiveKit worker,推理进程共享) | ~0.4GB(+共享 0.8GB 一次) | 同上 | KWS关:min(38,16)=**16 路** | KWS关 ~64 路(CPU 限) |
| B(进程内多会话) | 基线 1.2GB + ~0.1GB/会话 | 同上,但同循环竞争 | KWS关 ~16 路(实际受 GIL/循环调度限,须压测) | 须压测 |

> 结论先行:**关 KWS 是 3~4 倍的容量杠杆**;**A1 的瓶颈是内存(每进程重复载 800MB 判停模型)**,
> A2/B 消除该重复后瓶颈转到 CPU 与外部依赖。

## 5. 外部依赖并发约束（须在改造前实测确认)

| 依赖 | 每会话用量 | 需确认的上限 |
| --- | --- | --- |
| FunASR(10090) | 2 条 WS 流(主 STT + 在线打断),持续推流 | 服务端 GPU 并发解码路数(决定全局 N 上限,很可能是**真正的天花板**) |
| LLM 网关 Qwen3-4B(10092) | 突发 1 并发请求/轮 | 网关吞吐(tokens/s)与并发 slot;N 路同时提问时 TTFT 退化曲线 |
| DashScope CosyVoice | 说话期 1 并发合成 | 账号级并发/QPS 配额(商务侧确认);池 size 需 ≥ 同时说话路数 |
| Qwen3-ASR(10091,可选栈) | 每轮 1 短连接 | 同 FunASR |

**建议在动代码前先做"外部容量摸底"**:用现有回放工具起 2/4/8 个独立进程(各自
`AGENT_SCENARIO` 注入不同录音、各绑不同 `WEB_UI_PORT`)打同一组远端,看 FunASR/LLM/TTS
在几路时开始退化——这一步**零代码改动**即可执行,数据直接决定 N 的现实上限与方案选型力度。

## 6. 三个候选方案

### 方案 A1:进程池 + 前置分配网关(每会话一进程)

- 结构:`[客户端 wss] → 网关(单端口 10099,asyncio/nginx-stream) → 进程池[P1..Pn]`,每个 Pi 就是
  今天的单会话 agent(`WEB_UI=0`,各绑内部端口),网关按"空闲进程"分配连接、满则排队/busy。
  进程池管理器负责预热(冷启动 ~10s 须提前载好)、健康检查、会话结束后回收重置(或重启进程)。
- 改动面:**agent 代码近零改动**(仅 §3 表中"日志路径/runs 目录加 id"两处小改);新增网关+池管理器
  (独立小组件,~200-400 行,不碰主链)。
- 优点:隔离性最好(一路崩不连坐);与现有单会话行为 100% 一致(49 次回放的验证直接继承);
  最快可交付。缺点:内存最贵(N×1.2GB);进程池/网关是新增运维面。

### 方案 A2:回归 LiveKit 原生 worker 模式(每 job 一进程,框架管调度)

- 结构:部署 LiveKit server(或云),agent 以 `start` 模式注册 worker;每用户一个 room,框架
  `proc_pool` 派 job 进程,**turn-detector 推理进程全 worker 共享**(框架原生能力),预热、回收、
  负载上报全现成。
- 客户端影响:**接入方式变**——C/MATLAB/Python 客户端现走自建 `/ws/audio`,需要(a)改造成
  LiveKit room 客户端,或(b)保留协议、加一个"WS↔room 桥"网关(把 PCM 转成 room 音轨)。
  (b)保护了三端客户端投资,但桥本身是一个新组件(含 WebRTC 栈)。
- 优点:内存最优、调度/伸缩/可观测是框架成熟能力、是这个代码库的"本来形态"(console 只是开发模式)。
  缺点:引入 LiveKit server 运维;客户端接入层工程量;`AppRuntime`/`webpanel` 单例在 job 进程内
  仍是单会话使用——恰好兼容,无需 per-session 化。
- 注意:`webpanel`(调试面板)在多 worker 下应仅运维用途,`WEB_UI=0` 默认关。

### 方案 B:进程内多会话(单进程 N 个 AgentSession)

- 把 `runtime`/`panel` 单例改 per-connection 实例(重构已聚拢状态,机械可行),`/ws/audio`
  每连接建独立 Session + tap 链;CosyVoice 池调大;日志/录音加 session_id。
- 优点:内存增量最小(~0.1GB/会话)。缺点:改动面最大(状态传递贯穿 webpanel/app 两层)、
  单进程故障连坐、N 路音频帧+KWS+录音在一个 GIL 下的实时性需要专门压测;聆听/打断这些
  实时敏感链路的回归成本高。
- 定位:**不作首选**;若未来内存成为硬约束、且 A2 已就位,可作为 job 内小并发(如 1 进程 2~4 路)的
  优化项再评。

### 对比总表

| 维度 | A1 进程池+网关 | A2 LiveKit 原生 | B 进程内多会话 |
| --- | --- | --- | --- |
| agent 代码改动 | ≈0(两处小改) | 小(部署形态+面板开关) | 大(状态 per-session 化) |
| 新增组件 | 网关+池管理器(自研小件) | LiveKit server(+可选 WS 桥) | 无 |
| 客户端改动 | **无** | room 化或经桥(桥则无) | 无 |
| 内存/会话 | ~1.2GB | ~0.4GB | ~0.1GB |
| 隔离性 | 最好 | 好(进程级) | 差 |
| 行为等价风险 | 最低(逐进程=现状) | 低(框架路径,但 room 音频链与 /ws/audio 链不同,需回归) | 高 |
| 交付速度 | **最快** | 中 | 慢 |

## 7. 推荐路线:两步走

1. **第一步(短期,建议本季度): A1**。用最小代价把"1 路"变"N 路"(N 先按 8核16GB+关KWS ≈ 10 路
   规划),客户端零改动,行为等价直接继承回放验证。前置动作:§5 外部容量摸底(零代码)。
2. **第二步(中期): A2 评估→迁移**。当 N 增长使内存成本显著、或需要多机/断线重连/正规调度时,
   迁移到 LiveKit 原生 worker;三端客户端经"WS↔room 桥"平滑过渡。A1 的网关此时演化为桥,
   投资不作废。
3. B 仅在 A2 落地后作为 job 内并发优化项再议。

## 8. A1 细化设计(供评审)

- **网关**:单一对外端口(10099,TLS 终结);职责=连接分配、心跳透传、busy/排队应答(复用
  PROTOCOL.md 的 `busy` 消息语义,客户端无感)、会话计数与指标。实现候选:asyncio 自研
  (与 `clients/python/xiaoge_client.py` 同栈,~300 行)或 nginx stream + 动态 upstream(少代码但
  分配策略弱)。倾向自研(需要"每进程同时只承载一路"的粘性分配)。
- **进程池管理器**:预热 N 个 agent 进程(`WEB_UI=0`、`XIAOGE_KWS_ENABLE_NATIVE=0`、
  `WEB_AUDIO=1`、内部端口 191xx、独立 `TURN_METRICS_LOG`/runs 前缀);就绪探测(内部
  `/ws/audio` 握手 `ready`);会话结束(客户端断开)后**重启进程**回收(比状态复位可靠,冷启动
  ~10s 在池内摊平);崩溃自动补位。
- **agent 侧仅两处小改**(届时按流程评审后实施,不在本文档范围内动手):runs/recordings 目录名
  加进程标识;(可选)`/ws/audio` 断开即主动结束会话并退出进程(配合"重启回收")。
- **容量保护**:池满时网关回 `busy`(现有客户端已处理该消息);排队为可选二期。
- **可观测**:网关输出每路 session_id→进程映射;各进程指标日志独立,汇总脚本离线合并。

## 9. 验证方案

1. **外部容量摸底**(改造前):2/4/8 进程并发回放打真机,记录 FunASR final 延迟、LLM TTFT、
   TTS TTFB 退化曲线 → 定 N 上限。
2. **并发功能回归**(A1 落地后):N 路同时注入**不同**历史录音(工具现成:`AGENT_SCENARIO`),
   断言各路 `turn_kpis.json` 与单路基线一致(turns/felt 同带)+ **互不串音**(各路 assistant.wav
   与其源录音的对话逻辑对应);另做"同时说话/同时打断"专项(N 路同刻注入含停止词录音)。
3. **浸泡**:4 路 × 2 小时长对话录音循环,盯内存増长/连接泄漏/池竞争日志。
4. 门禁沿用:87 单测 + lint-ours + 行数门禁不受影响(网关/池管理器纳入 ourcode.txt)。

## 10. 风险清单

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| FunASR 服务端并发解码路数不足(2N 条流) | 高(可能是真天花板) | §9-1 先摸底;不足则加卡/降 N/在线打断流可降级关闭(牺牲早打断) |

| DashScope TTS 配额/限流 | 中 | 商务确认配额;池竞争已有冷建兜底+恢复路径(评审#2 修复) |
