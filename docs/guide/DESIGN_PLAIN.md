## 1. 整体是怎么跑起来的

### 三层楼的结构

把整个系统想象成一栋三层楼：

```
┌─────────────────────────────┐
│  第三层：浏览器（你看到的）  │  显示对话、麦克风按钮、气泡
├─────────────────────────────┤
│  第二层：网关（收发室）      │  负责转接，判断谁能进来
├─────────────────────────────┤
│  第一层：Agent 进程（大脑）  │  真正在"思考"和"说话"的地方
└─────────────────────────────┘
```

**第三层（浏览器）**：你能看见、能点击的界面。麦克风采集你的声音，把音频发给第二层。

**第二层（网关/收发室）**：接收浏览器发来的音频，转发给第一层；同时把第一层产生的回复（语音、文字）转发回浏览器。还负责一件重要的事：**同一时间只让一个用户进来**，第二个人来了就告诉他"忙，请刷新"。

**第一层（Agent 进程/大脑）**：接收音频 → 转文字 → 交给 LLM 思考 → 生成回答 → 合成语音 → 送出去。所有真正的智能都在这层。

## 2. 音频是怎么从嘴巴传到 AI 的

### 想象一条流水线，音频经过多道"工序"

```
你说话（麦克风）
    │
    ▼
【工序①】静音门（MuteGate）
    你按了关麦？→ 把真实声音换成"空气"（全零帧）
    没关麦？→ 原样通过
    │
    ▼
【工序②】关键词检测（KWS）
    同时监听有没有唤醒词（比如"小歌"）
    → 音频原样继续往下，唤醒词触发另外的动作
    │
    ▼
【工序③】在线快速 ASR（旁路 2pass）
    把音频复制一份，喂给一个"只求快不求准"的识别服务
    → 专门用来判断：你是不是在压着 AI 说话、要不要打断它
    → 音频原样继续往下
    │
    ▼
【工序④】主 ASR（真正的转写）
    高质量识别，结果会进入对话上下文
    → 这才是"小歌听懂你说了什么"的地方
```

**重点**：工序②③是"旁路监听"——它们不改变音频，只是悄悄监听并做判断，音频继续原样往下走。就像流水线上有个质检员在旁边观察，货物并没有因此停下来。

### 为什么要两个 ASR（工序③和④）

| | 旁路快速 ASR（工序③） | 主 ASR（工序④） |
|---|---|---|
| 速度 | 很快，~0.3秒就有结果 | 较慢，~1-2秒 |
| 质量 | 一般，容易识错 | 高，准确 |
| 用来干嘛 | 判断"要不要打断 AI 播报" | "小歌听懂你说的话" |
| 结果进对话吗 | ❌ 永远不进 | ✅ 进入对话 |

类比：旁路 ASR 像保安——只需要判断"这个人是不是要进来"，不需要知道他说了什么具体内容；主 ASR 像接待员——要听清楚你说的每一个字。

## 3. AI 怎么知道你说完了——判停

### 问题

你说话中间会有停顿，AI 不能一检测到停顿就以为你说完了（你可能只是换气）；但也不能等太久（那延迟就太高了）。

### 两道关卡

**第一道关卡：VAD（声音活动检测）**

VAD 就像一个"声音红绿灯"：
- 你在说话 → 绿灯
- 停顿超过 **0.35 秒** → 红灯（可能说完了）

但 0.35 秒的停顿太短，可能只是换气或思考，不能马上提交。

**第二道关卡：EOU 模型（语义判断）**

VAD 亮红灯后，EOU 模型读一下你已经说的内容，判断"这句话语义上说完了吗"：

```
你说了"今天天气怎么" → EOU：没说完（prob低）→ 再等，最多等 0.6s
你说了"今天天气怎么样" → EOU：说完了（prob高）→ 0.3s 后提交
```

### 两种情况的时间线

```
情况A：话说完整了
  你: "今天天气怎么样。"
  VAD: ─────说话──────[停0.35s]→红灯
  EOU: 判断→语义完整→等0.3s→提交给AI回答    ← 总延迟约0.65s

情况B：话没说完
  你: "今天天气怎么"（停顿了一下思考）
  VAD: ─────说话──────[停0.35s]→红灯
  EOU: 判断→语义不完整→继续等→等满0.6s→强制提交
```

### 抢跑模式（preemptive TTS）

开启后，VAD 刚亮红灯就立刻让 LLM 开始思考（用当前最佳的转写文本），不等 ASR 出 final 结果。

- **好处**：回复更快，首响延迟低
- **坏处**：如果你只是换气又继续说，AI 可能已经在基于"半句话"生成回复了，导致回复片段感

## 4. 你说话能打断 AI——打断

### 场景

AI 正在滔滔不绝说话，你想让它停下来或者直接说别的。

### 三条打断路径，速度不同

把它比作三个"报警按钮"，分别在不同时间触发：

```
你开口说话
    │
    ├─【按钮A】最快（~0.3秒）：旁路快速 ASR
    │    一边监听你说话，文字一出来就判断：
    │    → 你说的是"停/好了/别说了"？→ 立刻强制掐断AI播放
    │    → 你说的字够多了（≥3个实义字）+ 你确实在说话（VAD确认）？→ 软打断
    │
    ├─【按钮B】中间（~1秒）：主 ASR 出完整转写后
    │    → 你说的是停止词？→ 强制打断
    │    → 你说的是"嗯/哦/对"这类附和？→ 清掉这条输入，不打断也不回复
    │
    └─【按钮C】最慢（~2秒）：进入AI思考前的最后拦截
         → 停止词/附和/语气词 → 跳过本次回复
```

**为什么三个按钮都保留？**

因为单靠一个不够可靠：
- 只有按钮A：旁路 ASR 质量差，可能误判
- 只有按钮C：太慢，用户早就不耐烦了
- 三个都有：速度和可靠性都兼顾，早触发体验好，晚触发做最后兜底

### VAD 佐证是什么

按钮A（旁路快速 ASR）有个防误判机制：

> 文字到了，但 VAD 说"用户根本没在说话"——那这个文字很可能是**噪声被误识**出来的，不能打断。

这叫"VAD 佐证"。VAD 就像一个人站在旁边看，快速 ASR 说"有人说话了"，VAD 说"我没看到有人开口"——那就当没发生，忽略掉。

### 聆听保护

有一个特殊情况：小歌在说"进入聆听模式了哦～"这类**受控播报**时，用户的语音不应该打断它。

就像你跟朋友说"稍等，我说完这句话"——这句话说完之前，中途插话无效。

## 5. 哪些话 AI 会忽略——拒识

### 三类会被忽略的输入

**第一类：停止词**

你说"停、好了、别说了、等等"——AI 停止播报，跳过本次回复，不生成任何答案。

词表里有 28 个词，还支持加前缀，比如"那别说了"也能识别（"那"是引导词，不影响"别说了"的判定）。

还有一个彩蛋：**"休庭"** 也在停止词表里——因为 FunASR 经常把"停"识别成"休庭"，所以两个都得管。

判定是**分段的**，不是整句匹配。比如你说"嗯，行了"：
- "嗯" → 附和字，允许
- "行了" → 停止词，命中
- 结论：整句算停止词，触发拒识

**第二类：背调词（语气词）**

你说"嗯""哦""哎""诶"——AI 不回复，但也不打断自己正在播报的内容。

逻辑是：你只是在点头示意"我在听"，并不是要说什么，所以 AI 安静记下，继续该干嘛干嘛。

**第三类：压话附和**

AI 正在说话，你插了一句"对对对""嗯嗯"——这种情况下也跳过回复。

但注意：同样是"对"，**在 AI 提问之后**说"对"是真实回答，不能拒识；只有在 AI 播报过程中说才按附和处理。所以这里有个条件判断："用户说话时 AI 正在播报吗？"

### 决策流程

```
你说了一句话
    ↓
停止词？
    是 → 强制打断 + 跳过回复（停止词路径）
    否 ↓
纯语气词（嗯哦噢啊…）？
    是 → 只跳过回复，不打断
    否 ↓
说话时 AI 在播报，且你说的全是附和字（对好是嗯…）？
    是 → 跳过回复
    否 ↓
正常进入 AI 思考，生成回复
```

## 6. 聊天气泡是怎么来的

### 用户气泡和 AI 气泡是两条独立的流水线

**用户气泡**（你说的话显示出来）：

```
你说话
  │
  ├─ 流式 ASR 出来的中间结果（边说边更新）
  │    → 气泡实时变长，像打字一样
  │
  └─ ASR 最终 final 结果
       → 定稿，气泡文字固定下来
       → 顺手去掉句首奇怪的标点（FunASR 有时会把上一句的句号带到下一句句首）
```

**AI 气泡**（小歌的回答显示出来）：

```
LLM 生成 token 流
  │
  ├─ 送去 TTS 合成语音（要去掉 markdown 格式，不然 TTS 会把 ** 读出来）
  │
  └─ 等全部生成完，再去掉 markdown，一次性推送到浏览器显示
       → 所以气泡是"一下子全出来"，不是逐字出现
```

### 气泡内容 ≠ LLM 看到的内容

这是一个重要设计决策：**显示净化，不影响 AI 理解**。

| | 用户气泡显示 | LLM 看到的 |
|---|---|---|
| 句首多余标点 | 去掉 | 保留原文 |
| AI 回复中的 markdown | 去掉 | 保留原文 |

原因：净化是为了显示好看，但 LLM 需要原始文本才能准确理解上下文。如果把 LLM 看到的文本也净化了，可能影响它对话意图的理解。

### 聆听期气泡特殊处理

小歌进入"聆听模式"（只听不回答）时：
- 用户说话的气泡：**不显示**（避免显示那些"被吞掉"的内容）
- 小歌的系统提示（"进入聆听模式了哦"）：**不显示为助手气泡**

## 7. 静音按钮是怎么工作的——MuteGate

> 详见通俗说明中已有的解释，这里补充位置逻辑。

### 为什么装在最里层

```
麦克风
  │
  ▼
【MuteGate】← 装在这里（最靠近麦克风）
  │
  ▼
KWS 监听
  │
  ▼
打断用的快速 ASR
  │
  ▼
主 ASR / VAD / 录音
```

因为它装在所有处理模块的**上游**，关麦时送出去的是静音帧，所有下游模块**同时**被隔离：
- KWS 听不到声音，不会误触发唤醒
- 快速 ASR 听不到，不会误触发打断
- 主 ASR 听不到，不会产生转写
- 录音录下的是静音，不会录到你不想录的内容

**一刀管住所有人**，不需要每个模块单独处理"现在是静音状态"。

## 8. 聆听模式是什么

### 场景

你和小歌聊天时，需要去接一个电话，或者和旁边的人说几句话，但不想关掉小歌。这时进入聆听模式：

> **小歌只听不说，把你说的话偷偷记下来，等你喊它"干活"再处理。**

### 四个状态

```
正常对话
    │
    │ 说"小歌聆听模式" 或 连续N轮很长的话
    ▼
聆听中（只听不说）
    │  你说的话进临时缓冲区，不进对话、不生成回复
    │  气泡不显示（避免显示"被吞掉"的内容）
    │
    │ 说"小歌干活了" 或 按通话键
    ▼
退出聆听
    │
    ├─ 你聊了很多内容？→ 小歌问："要整理一下吗？"
    │       说"要" → 小歌把刚才的内容总结一遍
    │       说"不用" → 直接回正常对话
    │
    └─ 没什么实质内容 → 直接回正常对话
```

### 三个保护机制

**① 退出尾巴处理**

你说"小歌干活了"，KWS 几乎立刻识别到。但 ASR 要晚 ~1.5 秒才出 final 结果，这条 final 里包含"小歌干活了"这几个字。

如果直接把这条 final 当成正常对话，小歌会回答"小歌干活了是什么意思"——显然不对。

所以退出时有个 1.5 秒的"尾巴窗口"：在这个窗口内到达的 final，把唤醒词之前的内容丢掉，唤醒词之后的内容保留（比如"小歌干活了，帮我查一下天气"，就只保留"帮我查一下天气"）。

**② 打断保护**

小歌说"进入聆听模式啦～"这句话的时候，你语音不能打断它。因为这是受控播报，说了一半被中断体验很奇怪。6 秒的保护窗口内，打断请求被屏蔽。

**③ 自动进入**

如果你连续几轮说了很长的话（比如在和别人说话），系统会自动判断"用户可能在和别人聊天，不是在和小歌说话"，自动进入聆听模式，不再追着你的每句话生成回复。

## 总结：各机制的关系

```
你开口说话
    │
    ├─→ 【MuteGate】关麦了？→ 停止，后面全不走
    │
    ├─→ 【KWS】唤醒词检测（聆听模式专用）
    │
    ├─→ 【旁路快速 ASR】→ 【打断判定-路径A】
    │         字够了 + 有人在说话 → interrupt()
    │
    └─→ 【主 ASR + VAD】
              │
              ├─ STT final → 【打断判定-路径B】
              │                   停止词 → interrupt()
              │                   附和词 → 清掉这一轮
              │
              └─→ on_user_turn_completed
                      │
                      ├─ 【聆听模式处理】→ 吞入缓冲 or 切分
                      ├─ 【拒识过滤】→ 停止词 / 背调 / 压话附和
                      ├─ 数字归一化（"12345" → "1、2、3、4、5"）
                      │
                      └─→ LLM 生成回复
                               │
                               ├─→ TTS 合成语音 → 播放
                               └─→ 气泡推送到浏览器
```

每一个模块都只做一件事，组合在一起形成完整的对话流。
